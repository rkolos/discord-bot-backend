# 8.2. Доступ к данным

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел описывает требования к контролю доступа для Frontend API и Admin API.

## 8.2.1 RBAC для Frontend API

- Доступ к гильдии должен проверяться через **TeamMember role check**.
- Роли: `Owner`, `Admin`, `Member` (см. `company_members` в `spec/04-01-postgresql.md`).
- Guards должны проверять:
  - принадлежность пользователя к компании/гильдии;
  - достаточность роли для операции.

## 8.2.2 Admin API Roles

- Админские роли: `admin`, `super_admin` (см. `admin_users`).
- Чувствительные действия (бан, impersonation, управление шардом) доступны только `super_admin`.

## 8.2.3 Принципы

- Проверка доступа должна выполняться **до** выполнения бизнес‑логики.
- Ошибка доступа возвращается с кодом `FORBIDDEN` или `INSUFFICIENT_PERMISSIONS`.

## 8.2.4 Публичный доступ к виджету по ID

- Эндпоинт **`GET /api/widgets/:widgetId`** (см. Frontend API, `ABOUT/API_SPEC_FRONT/10-widget-endpoints.md` — Get Widget by ID) является **публичным** (без обязательной авторизации) для рендеринга виджета.
- Обязательная проверка: перед выдачей данных по виджету необходимо проверить флаг **`server_settings.allow_public_widgets`** гильдии, к которой принадлежит виджет.
- Если `allow_public_widgets === false`: эндпоинт должен возвращать **403 Forbidden** даже при валидном существующем `widgetId`.
- Если `allow_public_widgets === true` и виджет существует — возвращать 200 и данные по контракту API.
