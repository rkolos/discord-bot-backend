# 6.3. Система каунтеров (Live Counters)

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел описывает обработку и обновление каунтеров в Discord‑каналах.

## 6.3.1 Очереди и задачи

- Все обновления каунтеров выполняются через BullMQ очередь:
  - `sn:{env}:workers:queue:counters:update` (см. `spec/04-03-redis-schema.md`)
- Producer: Frontend API / Scheduler  
- Consumer: Background Worker

**Приоритизация:** Задачи от гильдий с планами `pro` и `enterprise` должны иметь повышенный приоритет в очереди. При добавлении задачи в очередь Producer передаёт параметр `priority` в зависимости от `subscription_tier` гильдии (например: enterprise > pro > free), чтобы BullMQ обрабатывал платных клиентов раньше при перегрузке.

**Payload задачи (минимум):**
- `counter_id`
- `guild_id`
- `channel_id`
- `type` (`stat|goal|clock`)

## 6.3.2 Алгоритм обновления

1. Получить агрегаты из ClickHouse по `guild_id` и типу каунтера.
2. Сформировать `channel_name` по шаблону `template`.
3. Отправить запрос в Discord API для обновления названия канала.
4. Обновить `current_value` и `updated_at` в PostgreSQL.

## 6.3.3 Rate Limiting

- Discord ограничивает обновления каналов (пример: **2 обновления / 10 минут**).
- Для соблюдения лимитов используется Redis‑рейт‑лимитер на уровне `channel_id`.
- Если лимит превышен:
  - задача откладывается (delay),
  - либо переносится в повторную попытку с backoff.

**Переименование канала вручную:** Если канал был переименован вручную администратором Discord (изменение `channel_name` не через бота), воркер при следующем запуске задачи по этому каналу должен: получить актуальное имя канала из Discord API; сравнить с локальным кэшем/значением в БД; при расхождении — обновить локальный кэш и при необходимости пересчитать/обновить каунтер по шаблону, чтобы избежать конфликтов и лишних обновлений.

### 6.3.3.1 Обработка 429 (Too Many Requests)

- При получении от Discord API ошибки **429 (Too Many Requests)** задача должна перемещаться в состояние **delayed** (не failed).
- Время ожидания — **экспоненциальный backoff** (например: 1 мин, 2 мин, 4 мин, … с ограничением по максимуму); при наличии заголовка `Retry-After` от Discord его значение учитывается (например, как минимальное время до повтора).
- После истечения delay задача снова попадает в очередь и обрабатывается с учётом приоритета (см. приоритизацию в 6.3.1).

## 6.3.4 Ошибки и статусы

- При ошибке Discord API статус каунтера переключается в `error`.
- При успешном обновлении статус `active`.
- Ошибки логируются с привязкой к `counter_id` и `guild_id`.

## 6.3.5 Удаление каунтера

При вызове **DELETE** `/api/guilds/:guildId/counters/:counterId` (Front API, см. `ABOUT/API_SPEC_FRONT/09-counter-endpoints.md`) бэкенд выполняет:

1. **Удаление записи в PostgreSQL** — запись каунтера удаляется из таблицы `counters` (каскады при необходимости заданы в `spec/04-01-postgresql.md`).
2. **Задача в BullMQ на Discord** — в очередь `sn:{env}:workers:queue:counters:update` (см. `spec/04-03-redis-schema.md`) либо в отдельную очередь для операций удаления ставится задача на попытку удаления или переименования канала в Discord по логике продукта (если канал создавался ботом — удалить; иначе при необходимости переименовать/очистить). Конкретный выбор очереди (та же или отдельная «cleanup») фиксируется в конфигурации и документации очередей.
3. **Очистка очереди от задач каунтера** — при удалении каунтера все отложенные (delayed) и ожидающие (waiting) задачи в этой очереди BullMQ, у которых в payload указан данный `counter_id` (или `counterId`), должны быть аннулированы (remove by job data). Это предотвращает обработку воркерами уже несуществующего каунтера и лишние обращения к Discord API.
