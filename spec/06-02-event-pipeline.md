# 6.2. Event Pipeline (Обработка событий)

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел описывает требования к pipeline событий от Discord до ClickHouse.

## 6.2.1 Поток данных

1. **Discord Gateway** → **Bot Service**
2. **Bot Service** → **Redis Stream** (`sn:{env}:bot-service:stream:discord:events`)
3. **Ingestor Worker** читает Stream, выполняет обогащение (Enrichment)
4. **Ingestor Worker** пишет батчи в **ClickHouse** (`raw_events`)

## 6.2.2 Enrichment (Обогащение)

Перед записью в ClickHouse Ingestor Worker должен обогатить события:

- получить из Redis‑кэша для `guild_id` актуальные `plan_tier` и `anonymize_user_data`;
- заполнить `retention_until` на основании `plan_tier`;
- при `anonymize_user_data = true` вычислить и записать `anonymized_hash`, не записывать чувствительные поля в открытом виде;
- выставить `is_bot_generated` по правилам Bot Service (например, флаг в payload или признак отправителя).

Источник истины: PostgreSQL (`guilds`, `server_settings`), Redis используется как кэш актуальных значений.

## 6.2.3 First Contact (холодный старт)

При получении **первого** события типа `GUILD_CREATE` или **первого сообщения** от гильдии, с которой воркер ещё не работал:

1. Воркер, как и обычно, пишет событие в ClickHouse (после обогащения).
2. **Обязательно** проверять наличие записи гильдии и её настроек в PostgreSQL (таблицы `guilds`, `server_settings`).
3. Если записи **нет** — инициировать задачу в **BullMQ** на создание дефолтного конфига гильдии (создание/обновление записей в PostgreSQL). Без этого запросы аналитики по этой гильдии будут возвращать 404 или 500.
4. Имя очереди BullMQ и формат задач — см. `spec/04-03-redis-schema.md` (очереди воркеров); при необходимости вводится отдельная очередь для «first contact», например `sn:{env}:workers:queue:guild:setup`.

Enrichment (6.2.2) берёт `plan_tier` и `anonymize_user_data` из кэша/PostgreSQL; при отсутствии записи гильдии кэш пуст. First Contact гарантирует, что запись появится до того, как фронт запросит аналитику.

## 6.2.4 History Ingestion (импорт истории сообщений)

После **успешного** выполнения задачи First Contact (создание/обновление записей в `guilds` и `server_settings`) необходимо поставить одну задачу в BullMQ в очередь `sn:{env}:workers:queue:history:sync` (см. `spec/04-03-redis-schema.md`). Payload задачи: `{ guild_id, discord_guild_id }` (или эквивалент для однозначной идентификации гильдии).

**Алгоритм воркера History Sync:**

1. Получить список текстовых каналов гильдии (тип `GUILD_TEXT` через Discord REST API).
2. Для каждого канала запросить последние N сообщений (N = `HISTORY_SCAN_DEPTH`, 100–500, см. `spec/10-03-konfiguraciya.md`).
3. Трансформировать каждое сообщение в формат события для `raw_events` (как MESSAGE_CREATE), с обогащением по правилам 6.2.2 (plan_tier, anonymize_user_data, retention_until, анонимизация).
4. Установить в каждом таком событии **`is_historical: true`** (поле `is_historical` в таблице `raw_events`, см. `spec/04-02-clickhouse.md`).
5. Писать в ClickHouse батчами (аналогично Ingestor); применять **дедупликацию по `message_id`** (см. 6.2.8).

**Обработка частичных данных:** для исторических данных недоступны события `VOICE_STATE_UPDATE` или `MEMBER_JOIN` (в точном времени). Воркер заполняет только события типа MESSAGE_CREATE.

**Приоритизация:** очередь `history:sync` должна иметь **самый низкий приоритет** в BullMQ (например, `priority: 10` или выше — чем больше число, тем ниже приоритет относительно `counters:update` и `guild:setup`), чтобы не мешать обработке Live-событий.

**Дедупликация:** при записи в `raw_events` гарантировать отсутствие дублей по сообщению: использовать стабильный `event_id`, производный от `(guild_id, channel_id, message_id)`, или проверять существование по `message_id` (в payload или отдельной колонке) перед вставкой. Так события, уже попавшие в ClickHouse из Live-потока, не будут задублированы при импорте истории.

## 6.2.5 Анонимизация (Privacy First)

До записи в ClickHouse должны быть выполнены правила анонимизации:

- Секретные токены и персональные данные не должны попадать в `raw_events`.
- `discord_user_id` допускается хранить, но если требуется обезличивание — использовать хеш.
- Поля `payload` должны быть очищены от чувствительных данных.

## 6.2.6 Батчинг

- Ingestor пишет события в ClickHouse **пакетами**.
- Параметры батчинга должны быть конфигурируемыми:
  - `batch_size`
  - `batch_interval_ms`
- Цель — минимизировать нагрузку на ClickHouse при сохранении приемлемой задержки.

## 6.2.7 Backpressure и надежность

При недоступности ClickHouse:

- Ingestor **не теряет события** и не подтверждает их в Redis Stream.
- Используется ретрай с backoff (настраиваемый).
- При превышении лимита ретраев события переводятся в **DLQ Stream**:
  - `sn:{env}:ingestor:stream:discord:events:dlq`

## 6.2.8 Идемпотентность

- Каждое событие должно иметь `event_id`.
- Ingestor должен избегать дублей при повторной доставке.
- Для событий типа MESSAGE_CREATE дедупликация должна учитывать Discord `message_id` (в т.ч. при пересечении импорта истории и Live-потока): одно и то же сообщение не должно быть записано дважды.
