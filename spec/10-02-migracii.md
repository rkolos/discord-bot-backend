# 10.2. Миграции

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел фиксирует требования к миграциям для PostgreSQL и ClickHouse.

## 10.2.1 PostgreSQL

- Использовать **TypeORM/Prisma migrations** (выбор фиксируется в проекте).
- Миграции должны быть версионированными и воспроизводимыми.
- Автосинхронизация схемы в продакшене запрещена.

## 10.2.2 ClickHouse

- Для ClickHouse используются SQL‑скрипты миграций.
- Миграции включают:
  - создание таблиц (`raw_events`, MV);
  - изменения схем;
  - создание индексов.
- **Добавление поля `is_historical`:** если таблица `raw_events` уже создана без этого поля, применить миграцию: `ALTER TABLE raw_events ADD COLUMN is_historical UInt8 DEFAULT 0` (см. `spec/04-02-clickhouse.md`, поле для History Ingestion).

## 10.2.3 Процесс применения

- Миграции применяются автоматически при деплое или через отдельный CI‑шаг.
- Для каждого окружения — отдельный набор подключений и конфигураций.

## 10.2.4 Синхронизация миграций

- **Миграции ClickHouse** (включая Materialized Views) применяются **строго после миграций PostgreSQL** для данного релиза/деплоя.
- Обоснование: MV и скрипты ClickHouse могут ссылаться на новые поля или структуры таблиц конфигурации в PostgreSQL (или на конфигурацию, которую читает Ingestor); применение миграций ClickHouse до обновления PostgreSQL может привести к ошибкам или неконсистентным данным.
- В CI/CD или скрипте деплоя должен быть явный порядок: сначала PostgreSQL migrations, затем ClickHouse migrations.
