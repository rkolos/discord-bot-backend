# 2.2. Описание компонентов

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

## Общая архитектурная стратегия

Для реализации системы выбран подход **NestJS Monorepo**. Это позволяет:
1.  **Разделять запуск и деплой**: Frontend API и Admin API собираются как независимые приложения и запускаются на разных адресах/портах.
2.  **Общий код (Shared Libraries)**: Сущности базы данных (TypeORM), DTO, фильтры ошибок, гварды и утилиты хранятся в общей библиотеке и используются обоими сервисами, исключая дублирование логики.
3.  **Единое управление**: Упрощает поддержку зависимостей и контроль версий во всем проекте.

---

## 1. Frontend API Service (NestJS)

Основной сервис для взаимодействия с конечными пользователями.

-   **Назначение**: Обработка запросов от клиентского дашборда.
-   **Доступность**: Публичный интернет (`api.server.ninja`).
-   **Аутентификация**: 
    -   Интеграция с **Discord OAuth2**.
    -   Использование **JWT** (Access + Refresh в HttpOnly Cookie).
-   **Ключевые функции**: 
    -   Управление настройками гильдий.
    -   Просмотр аналитики (чтение из ClickHouse).
    -   Настройка каунтеров и виджетов.
-   **Безопасность**: Обязательная проверка прав пользователя в гильдии через Guards.

## 2. Admin API Service (NestJS)

Сервис для внутреннего администрирования и мониторинга системы.

-   **Назначение**: Управление платформой, пользователями, гильдиями и мониторинг состояния системы.
-   **Доступность**: **Строго через VPN**. Не имеет публичного IP-адреса.
-   **Аутентификация**: Внутренняя система прав (Admin Roles), отдельная от пользовательского API.
-   **Ключевые функции**: 
    -   Мониторинг здоровья системы (System Health).
    -   Управление лимитами гильдий и тарифными планами.
    -   Прямой доступ к управлению ботами (Bot Fleet Management).
-   **Изоляция**: Развернут на отдельном внутреннем адресе (например, `admin-api.internal.server.ninja`).

## 3. Bot Service (Discord.js)

Сервис взаимодействия с Discord API.

-   **Назначение**: Поддержание соединения с Discord Gateway через ShardingManager.
-   **Технологии**: `discord.js` v14+.
-   **Потоки данных**: 
    -   **Ingress**: Прием событий (сообщения, голосовые каналы) и их отправка в **Redis Stream** для последующей обработки.
    -   **Egress**: Прием команд на изменение состояния (например, обновление названия канала) через Redis/BullMQ.
-   **Масштабирование**: Поддержка множества инстансов бота для обработки большого количества гильдий.

## 4. Ingestor Worker

Высокопроизводительный сервис обработки потоковых данных.

-   **Назначение**: Перенос данных из очередей в аналитическое хранилище.
-   **Механизм**: 
    -   Вычитывает "сырые" события из **Redis Stream**.
    -   Выполняет минимальную трансформацию и анонимизацию данных.
    -   Производит пакетную вставку (Batch Insert) в **ClickHouse** для минимизации нагрузки на диск.
-   **Отказоустойчивость**: Обработка Backpressure — если ClickHouse временно недоступен, данные остаются в Redis Stream до восстановления связи.

## 5. Background Worker (BullMQ)

Сервис обработки фоновых задач и расписаний.

-   **Назначение**: Выполнение ресурсоемких операций, которые не должны блокировать API.
-   **Ключевые задачи**:
    -   **Обновление каунтеров (Live Counters)**: Сбор агрегатов из ClickHouse -> Форматирование шаблона -> Запрос к Discord API через Bot Service.
    -   **Синхронизация данных**: Регулярное обновление информации о пользователях и ролях в PostgreSQL.
    -   **Billing**: Проверка статусов подписок и применение ограничений.
-   **Ограничения**: Строгое соблюдение Discord Rate Limits (например, 2 обновления канала в 10 минут) через механизмы задержек BullMQ.
