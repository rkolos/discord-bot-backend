# 7.2. Платежная система (Billing MVP)

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел описывает минимально необходимую логику биллинга.

## 7.2.1 Базовые сущности

- Таблица `companies` и связанные таблицы описаны в `spec/04-01-postgresql.md`.
- Тарифы фиксируются через `subscription_plans` и `user_subscriptions`.
- Лимиты использования — через `usage_limits`. Эталонные лимиты для каждого плана хранятся в справочнике в `spec/04-01-postgresql.md` (таблица `plan_limits`); Background Worker и другие сервисы сравнивают `usage_limits` с этими значениями без хардкода в коде.

## 7.2.2 Логика Billing MVP

- **Ручное переключение планов** (free/pro/enterprise) допускается как временное решение.
- Источник истины для текущего плана — `user_subscriptions`. Значения лимитов плана берутся из БД (таблица `plan_limits`); изменение лимитов плана выполняется только правкой данных в БД, без правок кода.
- Изменение плана должно:
  - обновлять `user_subscriptions`;
  - пересчитывать/синхронизировать `usage_limits` с новым планом;
  - отражаться в API ответах (`/api/me/subscription`, `/api/me/usage`).

## 7.2.3 Задел под webhooks

- В архитектуре должен быть предусмотрен слой интеграции под внешние платежные системы (например, Stripe).
- Минимальный интерфейс:
  - обработка событий `subscription.updated`, `invoice.paid`, `invoice.payment_failed`.
- Реализация webhooks может быть отложена, но структура должна быть готова к расширению.

## 7.2.4 Поведение при превышении лимитов

- Проверка лимитов выполняется при создании/включении сущности (каунтер, виджет и т.д.); эталонные значения лимитов берутся из справочника в БД (`plan_limits`).
- Если для данного `guild_id` (и связанного с гильдией плана владельца) лимиты плана превышены (например, по количеству серверов, каунтеров или иных квот):
  - Новые сущности, зависящие от лимита (например, **новые каунтеры**), создаются в статусе **`inactive`**.
  - В ответ/событие возвращается ошибка с кодом **`BILLING_LIMIT_REACHED`**.
