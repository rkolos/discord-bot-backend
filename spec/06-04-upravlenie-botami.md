# 6.4. Управление ботами (Bot Fleet)

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел описывает требования к управлению бот‑инстансами и шардированию.

## 6.4.1 Shared vs Premium Instances

- **Shared Instance** — общий бот для бесплатных гильдий.
- **Premium Instance** — выделенный бот/инстанс для premium клиентов.
- Логика маршрутизации гильдии к инстансу определяется `subscription_tier` и правилами продукта.

### 6.4.1.1 Миграция гильдии на Premium

- При смене плана гильдии на **Enterprise** в PostgreSQL:
  1. **Background Worker** (или отдельный процесс, подписанный на изменения подписки) обнаруживает смену плана.
  2. Отправляет в **Bot Service** команду через очередь (например `sn:{env}:workers:queue:bot:commands`, см. `spec/04-03-redis-schema.md`) на:
     - **«отключение»** гильдии от Shared-бота (leave guild или прекращение обработки событий гильдии на Shared);
     - **«подключение»** гильдии к выделенному Premium Instance (приглашение бота на Premium-инстансе в гильдию или переключение маршрутизации).
  3. Состояние гильдии в БД должно оставаться консистентным: обновляется `instance_id` или флаг/поле, указывающее на Premium-инстанс.

## 6.4.2 Шардирование

- Используется **ShardingManager** (Discord.js) с динамическим расчетом шардов.
- Статусы шардов должны быть доступны через Admin API (`/api/system/shards`).
- Статус хранится и обновляется на основе событий Gateway:
  - `online`, `handshaking`, `disconnected`, `error`.

**Heartbeat:** Каждый шард (Shard) должен записывать в Redis свой статус и время жизни (timestamp) не реже чем каждые **30 секунд**. Назначение: корректное отображение состояния шардов в Admin API (`/api/system/shards`), в том числе обнаружение «зависших» шардов, если heartbeat прекратился. Формат ключа и полей — см. `spec/04-03-redis-schema.md` (heartbeat шардов).

## 6.4.3 Статусы инстансов ботов

Для **инстансов ботов** (Bot Fleet / воркеры), в отличие от статусов шардов Gateway, используется перечень:

- **INITIALIZING** — инстанс запускается, подключается к Discord, ещё не готов обрабатывать гильдии.
- **READY** — инстанс готов, принимает события и команды.
- **RATE_LIMITED** — инстанс временно ограничен Discord API (rate limit).
- **DISCONNECTED** — инстанс отключён от Gateway или не подключён.

Эти статусы используются в мониторинге и в эндпоинтах состояния системы (например, Admin API system health), чтобы различать этап инициализации, готовность, ограничение по rate limit и отключение.

## 6.4.4 Обработка ошибок подключения

- При получении `401 Unauthorized` от Discord API:
  - пометить гильдию как `status = error` в PostgreSQL;
  - проставить `is_bot_in_guild = false`;
  - обновить время последней ошибки.
- При восстановлении соединения статус должен возвращаться в `active`.

## 6.4.5 Обработка события GUILD_DELETE

При получении от Discord Gateway события **GUILD_DELETE** (бот удалён с сервера) система выполняет:

1. **Обновление гильдии в PostgreSQL:** установить для соответствующей гильдии `status = 'inactive'` и `is_bot_in_guild = false` (см. `spec/04-01-postgresql.md`).
2. **Задача на деактивацию ресурсов:** поставить задачу в BullMQ (или внутреннюю очередь) на деактивацию всех каунтеров и виджетов этой гильдии — пометить их как inactive, прекратить постановку задач на обновление. Сами записи в БД при этом не удаляются; удаление выполняется по политике очистки или при ручном удалении гильдии через Admin API. В рамках этой задачи при необходимости выполняются попытки удаления или переименования каналов в Discord по той же логике, что и при удалении каунтера (см. `spec/06-03-sistema-kaunterov.md`, раздел 6.3.5).

## 6.4.6 Наблюдаемость

- Все изменения статусов шардов и ботов должны логироваться.
- Ошибки должны отображаться в Admin API (system health).
