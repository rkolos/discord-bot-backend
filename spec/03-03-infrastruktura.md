# 3.3. Инфраструктура

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

## Контейнеризация и запуск

- **Docker** — единый формат поставки и запуска всех сервисов.
- **Docker Compose** (для dev/stage) как базовый способ оркестрации.
- Конфигурация сервисов задается через переменные окружения, без хардкода адресов.

## Размещение и сеть (DigitalOcean Droplets)

- **Раздельные хосты (выбранный вариант):**
  - **Host A:** Frontend API + Admin API (два NestJS приложения).
  - **Host B:** Bot Service + фоновые воркеры (Ingestor, Counters).
  - **Host C:** PostgreSQL + Redis + ClickHouse (только во внутренней сети).
- **Сетевые ограничения:**
  - Все базы данных доступны **только** из приватной сети/VPC.
  - Публичный доступ открыт **только** для Frontend API.
  - Admin API доступен **только** через VPN (белый список IP или private network).

## Сетевые политики (Security Groups)

- **Host A (API):** Исходящий доступ разрешён **только** на Host C (PostgreSQL, Redis, при необходимости ClickHouse для чтения). **Прямой доступ с Host A на Host B (Bot Service) запрещён** даже внутри VPC — для минимизации вектора атаки.
- Bot Service недоступен с API-хоста по сети; взаимодействие API с ботом — только через Redis на Host C.

## Ресурсные требования (сбалансированный уровень)

- **Host A (API):** 2 vCPU / 4–8 GB RAM / SSD 40–80 GB.
- **Host B (Bot + Workers):** 2 vCPU / 4–8 GB RAM / SSD 40–80 GB.
- **Host C (DB):** 4 vCPU / 16 GB RAM / SSD 200+ GB (под ClickHouse и PostgreSQL).
- При росте нагрузки допускается горизонтальное масштабирование API и воркеров.

## Раздельные адреса API

- **Frontend API** размещается на публичном адресе и доступен из интернета.
- **Admin API** размещается на отдельном адресе и доступен только через VPN.
- Базовые URL для Frontend API и Admin API задаются через переменные окружения.

## Disaster Recovery (Аварийное восстановление)

### Поведение при отказе ClickHouse

- **Ingestor Worker** при недоступности ClickHouse переходит в режим **накопления в Redis Stream** (Backpressure): продолжает читать события из Stream, но не отправляет вставки в ClickHouse; данные остаются в Stream до восстановления связи.
- Обязателен **мониторинг заполнения памяти** (Memory Limit) Redis/Stream — при приближении к лимиту задействовать алерты и, при необходимости, политику отбрасывания старых данных или отключения приёма новых событий от Bot (опционально, с явным описанием в runbook или конфигурации).
- **Основные функции управления (Auth, Settings)** работают через PostgreSQL и не зависят от ClickHouse — при отказе аналитической БД или Ingestor Worker они продолжают работать в штатном режиме.
