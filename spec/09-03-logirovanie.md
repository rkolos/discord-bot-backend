# 9.3. Логирование

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел фиксирует требования к логированию.

## 9.3.1 Формат логов

- Формат: **JSON**.
- Обязательные поля:
  - `timestamp` (ISO 8601)
  - `level` (`info|warn|error|debug`)
  - `message`
  - `service`
  - `request_id` (если доступен) — см. Correlation ID (x-request-id) ниже.

## 9.3.2 Correlation ID (x-request-id)

Для сквозной отладки одного пользовательского запроса через все компоненты системы (API, Redis, Worker, Bot, Ingestor, ClickHouse) используется единый идентификатор запроса.

- **Frontend API** генерирует или пробрасывает заголовок **x-request-id** для каждого входящего запроса.
- При постановке задачи в BullMQ **x-request-id** передаётся в payload или в метаданных задачи (job opts), чтобы воркеры и Bot Service использовали тот же идентификатор.
- **Bot Service** при обработке команды от воркера логирует и при необходимости передаёт **x-request-id** дальше (в логи и при записи в ClickHouse, если событие/логи пишутся в CH).
- В логах и в ClickHouse (если туда пишутся трейсы/события) поле **request_id** должно содержать этот идентификатор для связи запроса через все 5+ компонентов (API, Redis, Worker, Bot, Ingestor, ClickHouse).
- Поле `request_id` в формате логов (9.3.1) — это и есть Correlation ID из заголовка x-request-id.

## 9.3.3 Уровни

- `info` — бизнес‑события и базовые метрики.
- `warn` — нестандартные, но не критичные ситуации.
- `error` — ошибки, требующие внимания.
- `debug` — подробные логи для разработки.

## 9.3.4 Маскирование данных

- Запрещено логировать:
  - пароли;
  - токены;
  - ключи шифрования;
  - персональные данные без необходимости.
- При необходимости — маскировать значения (например, `****`).
