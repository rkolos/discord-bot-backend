# 8.1. Шифрование

> **Важное примечание:** Перед началом реализации необходимо детально изучить всю документацию в папке `ABOUT/` и её подпапках (`API_SPEC_ADMIN`, `API_SPEC_FRONT`), а также ознакомиться с уже описанными пунктами в папке `spec/` для полного понимания контекста и текущих архитектурных решений.

Раздел описывает требования к шифрованию чувствительных данных.

## 8.1.1 Bot Token

- Поле `bot_token` должно храниться **только в зашифрованном виде**.
- Использовать **AES-256-GCM**.
- Хранить результат в `server_settings.bot_token_encrypted` (см. `spec/04-01-postgresql.md`).

## 8.1.2 Формат хранения

Минимальный набор данных для расшифровки:

- `ciphertext`
- `iv`
- `auth_tag`

Единый формат значения поля `server_settings.bot_token_encrypted` в PostgreSQL — строка:

`v1:base64(iv):base64(auth_tag):base64(ciphertext)`

Префикс `v1:` обязателен для поддержки будущей ротации ключей (при смене ключа можно ввести `v2:` и т.д.).

## 8.1.3 Управление ключами

- Ключ шифрования хранится **только** в переменных окружения или Secret Manager.
- **Encryption Key не передаётся между сервисами.** Каждый сервис получает ключ самостоятельно:
  - **Bot Service** — для расшифровки токена при работе с гильдией;
  - **Admin API** — для записи/обновления зашифрованного токена (например, при имперсонации или настройке).
- Источник ключа: **Environment Variables** или **Secret Manager** (Kubernetes Secret / Vault / облачный Secret Manager). Конкретный механизм может зависеть от окружения; передача ключа по HTTP или между сервисами не допускается.
- Ротация ключей должна быть поддержана (например, через версионирование ключей).
- Ключи не логируются и не возвращаются в API.
