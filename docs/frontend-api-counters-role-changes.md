# Изменения API: счётчики по ролям (Role Specific Counters)

Краткий список изменений в Frontend API для поддержки счётчиков по ролям (например «Админов: 4») и рекомендации по применению на фронте.

---

## 1. Новое значение метрики и поле в ответе

### Изменения

- **Метрика** `metric`: добавлено значение `"role"`.
- **Ответ счётчика**: во всех ответах с объектом счётчика добавлено поле **`roleId`** (`string | null`).

### Где встречается

- `GET /api/guilds/:guildId/counters` — список счётчиков.
- `POST /api/guilds/:guildId/counters` — создание (тело и ответ).
- `PATCH /api/guilds/:guildId/counters/:counterId` — обновление (тело и ответ).

### Рекомендации

1. **Типы/интерфейсы**  
   В типе счётчика (Counter) добавить:
   - в union метрики значение `'role'`;
   - поле `roleId: string | null`.

2. **Список счётчиков**  
   - Отображать счётчики с `metric === 'role'` так же, как остальные (например, подпись «По роли» или название роли, если есть маппинг `roleId → name`).
   - Поле `roleId` можно использовать для показа названия роли (см. п. 6).

3. **Обратная совместимость**  
   Старые счётчики приходят с `metric !== 'role'` и `roleId: null`. Не требовать `roleId` в UI для таких записей.

---

## 2. Создание счётчика (POST)

### Тело запроса

- **`metric`**: можно передавать `"role"`.
- **`roleId`** (optional): Discord Role ID (Snowflake, строка). **Обязательно**, если `metric === "role"`. Не передавать или передавать `null`, если метрика не `"role"`.

Пример для счётчика по роли:

```json
{
  "channelId": "1234567890123456789",
  "type": "stat",
  "metric": "role",
  "roleId": "9876543210987654321",
  "template": "Админов: {count}"
}
```

### Ошибки валидации (422)

- `metric === 'role'` и не передан `roleId` → ошибка по полю `roleId` (например, «roleId is required when metric is role»).
- `metric !== 'role'` и передан `roleId` → ошибка по полю `roleId` (например, «roleId must be empty when metric is not role»).

### Рекомендации

1. **Форма создания счётчика**
   - В селекторе типа/метрики добавить вариант «По роли» / «Участников с ролью» с `metric: 'role'`.
   - При выборе `metric === 'role'`:
     - показывать поле выбора роли (селект/комбобокс);
     - отправлять в теле выбранный Discord Role ID в `roleId`;
     - валидировать на клиенте: при `metric === 'role'` поле роли обязательно.
   - При выборе любой другой метрики:
     - не показывать выбор роли (или скрывать/очищать);
     - не отправлять `roleId` или отправлять `null`.

2. **Шаблон**  
   Для метрики `role` шаблон по смыслу такой же, как у других счётчиков: плейсхолдер `{count}` (например, «Админов: {count}»).

---

## 3. Обновление счётчика (PATCH)

### Тело запроса

- **`metric`**: можно передавать `"role"`.
- **`roleId`** (optional): при смене метрики на `"role"` нужно передать валидный Role ID; при смене с `"role"` на другую метрику — не передавать или `null`.

### Рекомендации

1. **Форма редактирования**
   - Если пользователь меняет метрику на «По роли» — показывать выбор роли и требовать выбор перед сохранением.
   - Если меняет с «По роли» на другую метрику — при отправке не передавать `roleId` или передавать `null`.
   - При редактировании только шаблона/канала и т.д. у счётчика с `metric === 'role'` можно при необходимости отправлять текущий `roleId` из ответа GET (для консистентности).

2. **Валидация**  
   Те же правила, что и при создании: при `metric === 'role'` в запросе должен быть валидный `roleId`, при ином `metric` — `roleId` не должен быть задан.

---

## 4. Ответы API

Во всех ответах, где возвращается объект счётчика, теперь есть поле:

- **`roleId`**: `string | null` — Discord ID роли; заполнен только при `metric === 'role'`.

Использовать его в карточках счётчиков, в формах редактирования и для маппинга «роль → название» (см. п. 6).

---

## 5. Где применять на фронте (чек-лист)

| Место | Что сделать |
|-------|-----------------------------|
| Типы/API-клиент | Добавить `'role'` в тип метрики и поле `roleId: string \| null` в тип счётчика. |
| Список счётчиков | Обрабатывать `metric === 'role'` и при наличии — показывать подпись/название по `roleId`. |
| Форма создания | Вариант «По роли», при нём — обязательный выбор роли и отправка `roleId`. |
| Форма редактирования | Учёт `metric`/`roleId` при смене типа и при предзаполнении формы. |
| Валидация форм | При `metric === 'role'` — обязательность роли; при ином `metric` — не отправлять `roleId`. |
| Обработка 422 | Показывать сообщения по полю `roleId` («required when metric is role» / «must be empty when metric is not role»). |

## 6. Откуда брать список ролей для выбора

Для селектора ролей при создании/редактировании счётчика с `metric === 'role'` нужен список ролей гильдии с полями `id`, `name` (и при желании `color`).

- **Сейчас**: роли гильдии приходят в ответе **`GET /api/guilds/:guildId/analytics`** в поле **`roleDistribution`**: массив `{ id, name, color, count }`. Этого достаточно для выбора роли (id — в `roleId`, name — для отображения в селекте). Минус: нужно вызвать analytics (с периодом from/to); список ограничен ролями, по которым есть данные за период.
- **Рекомендация**: если бэкенд добавит отдельный эндпоинт **`GET /api/guilds/:guildId/roles`** (список всех ролей гильдии), использовать его для селектора ролей при создании/редактировании счётчика. До появления такого эндпоинта можно использовать `roleDistribution` из analytics.

Маппинг «roleId → название» для списка счётчиков можно строить из того же источника (analytics или будущий GET roles).

## 7. Краткая сводка по полям

| Поле | Тип | Где | Когда обязателен / как использовать |
|------|-----|-----|-------------------------------------|
| `metric` | `'members' \| 'messages' \| 'voice' \| 'online' \| 'idle' \| 'dnd' \| 'offline' \| 'role'` | Запрос и ответ | В запросе при создании/обновлении: при выборе «По роли» — `"role"`. |
| `roleId` | `string \| null` | Запрос и ответ | В запросе: обязателен только при `metric === 'role'`; при остальных метриках не передавать или `null`. В ответе — всегда присутствует, для счётчиков не по роли — `null`. |
